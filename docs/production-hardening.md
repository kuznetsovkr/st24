### Диагностика до изменений

| Компонент | Наблюдение |
| --- | --- |
| SSH | Порт 22, `PermitRootLogin yes`, `PasswordAuthentication yes`; отдельное подключение с принудительным publickey и выключенными парольными методами успешно |
| Firewall | UFW неактивен, но в iptables есть цепочки ISPmanager; это не означает полного отсутствия фильтрации |
| Сохранённые правила UFW | Кроме сайта и SSH разрешены ISPmanager, FTP, DNS и почтовые порты; одного `ufw enable` для целевой политики недостаточно |
| Публичные слушающие сокеты | FTP 21, SMTP 25/465/587, POP3 110/995, IMAP 143/993, DNS 53 TCP/UDP, панель 1500/1501, SSH 22 и сайт 80/443; это данные `ss`, не проверка достижимости каждого порта снаружи |
| Внутренние сокеты | API 4000, PostgreSQL 5432, Redis 6379, MySQL 3306/33060 и Apache 8080 слушают loopback |
| Fail2ban | Активен; jail `sshd` и `exim-isp` |
| DNS магазина | NS домена — `ns1.reg.ru` и `ns2.reg.ru`; MX не найден при внешнем DNS-запросе |
| DNS самого VPS | `systemd-resolved`, upstream DNS провайдера, а не локальный BIND |
| Приложение | PID API остался 743; в изученном коде нет использования SMTP/MySQL/Apache как backend-зависимостей |

Эти наблюдения помогают выбрать кандидатов на отключение, но не заменяют
проверку конфигурации nginx, системных задач и зависимостей служб.
На момент этой первоначальной диагностики отключение BIND/Apache/MySQL, почты,
FTP или панели ещё не выполнялось; последующий этап описан ниже.

## Исходный план и ограничения

1. Предпочтительно иметь независимую веб/VNC-консоль FirstVDS. Если владелец
   явно согласовал работу без неё, сначала проверить независимый системный
   таймер отката и сохранить SSH-сеанс, затем проверить второе подключение
   по ключу. Это не заменяет консоль при отказе ОС/диска/сети. Не менять порт
   SSH и не удалять действующий ключ.
2. В root-only каталоге вне репозитория сохранить конфиги SSH/UFW,
   IPv4/IPv6-правила firewall и состояния связанных служб. Подготовить
   ограниченный по времени автоматический откат, который не зависит от
   сохранности SSH-сеанса; проверить его до применения.
3. Согласовать сетевую политику: публично только TCP 22, 80 и 443,
   исходящие соединения разрешены, loopback и established/related сохранены,
   IPv6 не оставлен без защиты. Учесть цепочки ISPmanager и Fail2ban:
   не использовать слепой `ufw reset`, `iptables -F` или очистку чужих правил.
   Проверить, что панель/её задачи не восстанавливают прежние разрешения.
4. Оставить вход по ключу и отключить парольные/keyboard-interactive методы
   SSH. Проверить `sshd -t` и эффективные настройки, включая Match/порядок
   include-файлов. Применять reload, не перезапускать сервер и не закрывать
   проверенный сеанс до успешного нового подключения.
5. До отмены автоматического отката проверить новое SSH-подключение,
   публичные HTTPS/HTTP, readiness, DNS самого VPS, работу backup watchdog
   и исходящий доступ к облаку/наблюдателю без печати секретов. Затем проверить
   ограничение лишних портов снаружи и сохранить итоговое состояние правил.
6. Отдельно согласовать отключение ненужных служб. До остановки проверить
   зависимости nginx/приложения, выпуск и продление TLS, DNS и задания панели.
   Сначала остановка/отключение автозапуска с проверкой магазина; удаление
   пакетов, данных MySQL, почтовых ящиков и конфигов — не часть первого шага.

## Что фактически применено

Исходники и эксплуатационные команды: [ops/security](../ops/security/README.md).
Сохранён root-only каталог `/root/karcher-access-hardening-20261017T134104Z`
с исходными SSH-конфигами, IPv4/IPv6-правилами и конфигурацией UFW.
Приватные SSH-ключи не копировались и действующие authorized keys не менялись.

- В раннем SSH drop-in `00-karcher-access.conf` заданы publickey и запрет
  password/keyboard-interactive, `PermitRootLogin prohibit-password`,
  `AuthenticationMethods publickey`. Проверены `sshd -t`, фактическая
  конфигурация и несколько новых внешних соединений без multiplexing.
  Отдельная попытка без ключа отвергнута с `Permission denied (publickey)`;
  пароль не отправлялся. Применён reload, а не restart SSH.
- Перед каждым этапом независимый systemd timer выполнил self-test обработчика.
  Перед изменением SSH и firewall отдельно ставились пятиминутные timers
  отката; после внешней проверки они отменены. Аварийный откат не потребовался.
  Сохранённый SSH-сеанс оставался доступен до окончания обеих фаз.
- Вместо включения UFW с устаревшими разрешениями использована отдельная
  nftables-таблица `inet karcher_ingress` с input priority `-10`. Она не даёт
  правилу ISPmanager для 1501 обойти default deny и не очищает его таблицы.
  Сравнение чужих правил до/после, игнорируя счётчики, подтвердило совпадение.
- Установлены только `nftables` и `libnftables1` из репозитория Ubuntu;
  остальные пакеты не обновлялись. Стандартный `nftables.service` заранее
  masked, чтобы он не загружал глобальный ruleset. Защита управляется отдельным
  `karcher-firewall.service`: `enabled / active (exited)`, `Result=success`.
  Unit прошёл `systemd-analyze verify`; настоящий reload проверен без потери
  нового SSH-доступа. Автозапуск настроен, но перезагрузка VPS не выполнялась.
