# Внешние HTTP-проверки магазина

Следующий слой после [оповещений о бэкапах](../backup/ALERTS.md): Cronitor
сам обращается к публичным HTTPS-адресам. На VPS для этого не нужно запускать
дополнительный процесс, открывать новые порты, давать root SSH внешнему сервису
или передавать management API key. Работающий backup watchdog не меняется.

## Две проверки

| Проверка | Публичный адрес | Что подтверждает |
| --- | --- | --- |
| Karcher — сайт | `https://xn---24-3edf.xn--p1ai/` | HTTPS, HTTP 200, HTML магазина и контейнер React |
| Karcher — API и база | `https://xn---24-3edf.xn--p1ai/api/health/ready` | HTTP 200, JSON `ok`, PostgreSQL и запись/чтение/удаление canary в uploads |

`/api/health/live` не заменяет readiness: Node может отвечать при недоступной
базе. URL берутся публичные, не `127.0.0.1` и не IP VPS: проверяется также
публичный DNS/HTTPS/nginx-маршрут. В readiness нет заказов, паролей или токенов.

Общие настройки: **HTTP**, **GET**, интервал **5 минут**, timeout **10 секунд**,
проверка SSL включена, redirects выключены, Notification List **default** с
уже подключённым Telegram. `failure_tolerance: 0` — тревога при первом
подтверждённом отказе; у HTTP checks grace heartbeat не применяется.
Не выставлять интервал короче разрешённого бесплатным планом и не подключать
Browser-based checks/платную подписку для этого этапа.

## Ввод в интерфейсе

1. Открыть создание монитора Cronitor, выбрать HTTP-проверку, **не Heartbeat**.
   В блоке **Request Details** тип должен быть **HTTP**.
2. Заполнить Name, Endpoint, Method, Interval и Request Timeout по параметрам выше.
   Group и Tags можно оставить пустыми, авторизация и cookies не требуются.
3. В Response/Event Assertions добавить условия из
   [cronitor-http-monitors.json](cronitor-http-monitors.json). В форме условие
   вводится по отдельным полям: например, `response.body`, `contains`,
   `Купить запчасти для Karcher` — без лишних кавычек вокруг значения.
4. Включить SSL verification, отключить follow redirects, назначить список
   получателей `default` **обоим** мониторам. Убедиться, что Telegram включён
   для рабочего/default environment аккаунта.
5. Если в UI нет места для условий или названия отличаются, сначала сверить
   экран, а не удалять проверки. Одного HTTP 200 недостаточно: так можно
   принять парковочную страницу хостинга или HTML вместо JSON API за успех.
6. Сохранить оба монитора. Для HTTP checks не нужны Telemetry URL и новый
   скрытый ввод на VPS. HTTP-запросы выполняет внешний сервис.

В JSON лежит **шаблон**, не подтверждение настроек аккаунта. Он не содержит
секретов и не применяется автоматически. Формат `schedule` соответствует
default Monitor API `2020-10-01`; с версией `2025-11-28` используется
`schedules: ["every 5 minutes"]`. Не отправлять шаблон в API с произвольной
версией и не использовать telemetry-only ключ для изменения мониторов.

## Кодировка HTML

Если русские буквы в сохранённом ответе Cronitor выглядят как `Ð…`, проверить
не только `<meta charset="UTF-8">`, но и HTTP-заголовок `Content-Type`.
Для UTF-8 HTML nginx должен явно отправлять `text/html; charset=utf-8`:
директива `charset utf-8;` задаётся в HTTPS server-блоке магазина.
Не подменять ожидаемую фразу испорченным текстом и не отключать условие.
Перед правкой сохранить исходный конфиг вне доступных nginx include-каталогов,
выполнить `nginx -t`, затем `systemctl reload nginx` и проверить публичный ответ.
Reload асинхронный: сразу после него ещё может ответить старый worker;
проверка должна учитывать короткий ограниченный переходный период.
Приложение и БД для этого не перезапускаются. Поведение директивы описано в
[документации nginx](https://nginx.org/en/docs/http/ngx_http_charset_module.html#charset).

## Приёмка без остановки магазина

1. Дождаться успешных **внешних** запусков обоих мониторов: проверить время,
   HTTP 200, нужные условия и включённые уведомления. Локальный preflight не
   доказывает доступность с узлов Cronitor; в этой итерации нужен именно их результат.
2. Для контролируемого теста временно заменить **одно условие нового монитора**:
   у сайта маркер на `KARCHER_HTTP_ACCEPTANCE_TEST_NOT_REAL_OUTAGE`, у API
   ожидаемый `status` на `acceptance-test-not-real-outage`.
   Не трогать адрес сайта, настройки бэкапов, БД, nginx и приложение.
3. Получить тревоги в Telegram. Сразу вернуть правильные условия из шаблона,
   дождаться следующих успешных запусков и обоих уведомлений о восстановлении.
   Тест делать, пока владелец у экрана: нельзя оставлять неверное условие,
   отключать магазин или маскировать настоящую ошибку ради теста.
   Если за 10 минут тревога не пришла, всё равно вернуть исходное условие
   и отдельно разбирать доставку. Уже подтверждённую реальную тревогу сайта
   из-за кодировки можно использовать для приёмки вместе с подтверждённым
   восстановлением: повторно ломать условие сайта для этого не нужно.
4. Подтвердить, что проверки продолжают выполняться по расписанию. Зафиксировать
   факт доставки и завершение приёмки; не объявлять мониторинг включённым по
   одному созданному JSON или успешному локальному запросу.

При изменении реального SEO-заголовка/HTML-контейнера магазина нужно пересмотреть
и соответствующий маркер, а не просто отключить тревогу. На HTTPS включена
проверка сертификата; поведение предупреждений о сроке зависит от настроек
Cronitor и отдельно подтверждается в панели, не тестируется отключением TLS.

## Границы

HTTP-проверка видит исходный HTML, **не исполняет React** и не доказывает
загрузку JS/CSS/chunks, работоспособность корзины, авторизации, checkout,
оплаты, доставки или Telegram-прокси. Для этого остаются browser smoke и
полный runner `monitor/`. Здесь также не проверяется свежесть `checkedAt`
относительно текущего времени: заголовок `no-store` снижает риск кеша, но не
заменяет проверку возраста ответа из существующего runner.

## Первичная проверка 17 октября 2026

С рабочей станции по публичному HTTPS получены: главная HTTP 200,
`text/html`, заголовок `Купить запчасти для Karcher`, контейнер `root`;
readiness HTTP 200, `application/json`, `Cache-Control: no-store`,
`status: ok`, `checks.postgres.status: ok`, `checks.uploads.status: ok`.
Владелец сообщил о сохранении обоих HTTP-мониторов и условий readiness.
На скриншоте монитора сайта подтверждены два внешних HTTP 200 с ошибкой
проверки русской фразы; владелец подтвердил доставку этой тревоги в Telegram.
В сохранённом Cronitor HTML кириллица была декодирована как Latin-1: такой же
результат воспроизведён с исходными UTF-8 байтами публичного ответа без charset.

С разрешения владельца добавлена только строка `charset utf-8;` в HTTPS
server-блок `/etc/nginx/sites-available/st24`. Исходный конфиг сохранён в
`/root/karcher-nginx-utf8-20261017T130805Z-verified/st24.before` внутри каталога
с правами `0700`. `nginx -t` успешен, выполнен плавный reload. API PID `743`
и master PID nginx `151593` не изменились; HTML совпал с исходным файлом.

В 20:11 по Красноярску повторная проверка публичных адресов с рабочей станции
подтвердила все 10 условий шаблона: HTML HTTP 200 с `charset=utf-8`, исходной
русской фразой и `root`; readiness HTTP 200, JSON `ok`, PostgreSQL/uploads `ok`,
`Cache-Control: no-store`. Затем владелец отдельно подтвердил, что оба
HTTP-монитора в Cronitor стали зелёными: успешные внешние запуски сайта
и readiness API после исправления кодировки подтверждены.
Восстановление сайта в Telegram и тревога/восстановление HTTP-монитора API
ещё требуют отдельного подтверждения владельца; зелёный статус сам по себе
не доказывает доставку этих уведомлений.
Владелец решил проверить оставшиеся уведомления самостоятельно и продолжить
другие работы. Приёмка доставки HTTP-уведомлений остаётся незавершённой;
временное тестовое значение `status` нельзя оставлять вместо рабочего `ok`.
