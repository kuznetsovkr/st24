# Хранение и безопасная очистка бэкапов

На текущем VPS согласованная политика включена 20 октября 2026 года; результаты
первого применения, облачных сбоев и проверки новых копий приведены ниже.
Для другой установки наличие кода не включает
очистку. Применение требует
согласования владельца, root-only `/etc/karcher-backup/retention.json` с
`enabled: true`, установки worker/unit и успешного проверочного запуска.
До этого `retention.py plan` только читает копии и записывает закрытый отчёт.

## Согласованная политика

- VPS: все полные plaintext + encrypted пары за последние **7 суток**.
- Облако: все наборы за последние **48 часов**, далее последний набор за каждый
  день в последних **30 календарных днях**, за каждую неделю в последних
  **12 календарных неделях** и за месяц в последних **12 календарных месяцах**.
- Календарные дни/ISO-недели/месяцы считаются по `Asia/Krasnoyarsk`, окна 7 суток
  и 48 часов — по реальному UTC elapsed time. Текущая неделя/месяц входят в лимит.
- Независимо от возраста сохраняются последняя подтверждённая копия,
  три самых новых набора и все закреплённые `pinned`.
- Первоначальные pins: `2026-10-17_04-57-48_UTC` (проверенное восстановление
  зашифрованного dump), `2026-10-17_14-06-57_UTC` (проверенное покрытие SSH/firewall)
  и `2026-10-19_11-17-59_UTC` (проверенная recovery-конфигурация).

Это объединение окон/точек, не несколько дубликатов одного набора. Пропущенные
дни не заполняются; обещания 30 существующих ежедневных копий в неполной истории
нет. Изменение pins или сроков требует отдельного согласования.

## Область очистки

Только новые полные пары с именами `YYYY-MM-DD_HH-MM-SS_UTC` в фиксированных
`/var/backups/st24`, `/var/backups/karcher-encrypted` и age-v1 экспорты в
`yadisk:karcher-backups-encrypted/v1`. В наборе разрешены строго три ожидаемых
обычных файла. Неизвестные объекты, legacy plaintext-only, `.partial`, отчёты,
root rollback snapshots и **вся** `yadisk:st24-backups` не удаляются.

В облаке удаление выполняется только для точно проверенного отдельного набора,
с явным `--yandex-hard-delete=false`: **в корзину**, не навсегда. Общий
`rclone cleanup`, удаление namespace root и массовые sync/delete не используются.
Корзина содержит в том числе личные данные владельца; этот worker её не очищает.
Свободная квота может не увеличиться сразу, место продолжает контролировать
storage watchdog. Поведение backend описано в [документации rclone](https://rclone.org/yandex/).

## Предохранители

1. Общий `/var/lock/st24-backup.lock` исключает одновременную архивацию/очистку.
   Занятый lock означает пропуск без удаления; старый статус не обновляется.
2. Последний запуск должен совпадать с `.last-success`, быть `verified/complete`
   в новом age-режиме и не старше 26 часов. Ошибка/незавершённый backup — запрет.
3. Все новые локальные пары проверяются по типам, root owner, `700/600`, SHA-256,
   отсутствию symlink/hardlink компонентов. Корни не могут быть перенаправлены.
4. Все облачные экспорты заново скачиваются в root-private temp и проверяются
   по внешним SHA-256, формату, recipient fingerprint и времени. При наличии
   локального ciphertext его хеши обязаны совпасть с облаком. HTTP-сбои чтения
   повторяются ограниченно; ни один ошибочный результат не считается успехом.
   Это не age decrypt/MAC: секретного ключа на VPS нет.
5. Отсутствующий pin, отсутствующая облачная recovery-точка, повреждённый или
   неполный распознанный набор останавливают всю очистку. Автоматической перезаписи
   или "починки" облака из локальной копии нет.
6. До первого удаления повторно проверяются checkpoint, состав облака, fingerprints
   всех остающихся экспортов и signatures локальных файлов. Перед удалением
   каждого облачного набора его listing перепроверяется ещё раз.
7. Нельзя удалить больше 100 наборов или больше половины распознанной истории
   за один запуск; это повод проверить план вручную. Pins/latest/последние три
   защищены дополнительно при применении, а не только при выборе кандидатов.
8. Локально удаляются только конечные три файла через directory FD и `O_NOFOLLOW`,
   затем пустой каталог, без recursive delete. Две стороны пары удаляются
   последовательно, не атомарно. При сбое операция останавливается; action journal
   сохраняется. Частично выполненное удаление требует проверки оператора, не
   продолжения вслепую; защищённые оставшиеся копии не участвуют в удалении.

## Файлы и расписание

- `retention.py` — `/usr/local/lib/karcher-backup/retention.py`, root:root `600`.
- `retention.example.json` — **шаблон с enabled=false**, не автоматическое разрешение.
- Настоящий config — `/etc/karcher-backup/retention.json`, root:root `600`.
- `karcher-backup-retention.service/.timer` — `/etc/systemd/system/`, root:root `644`.
- Timer: ежедневно **08:15 по Красноярску**, `01:15 UTC` / `04:15 Europe/Moscow`,
  после backup 07:30 по Красноярску. Persistent, timeout worker 20 минут.
- `/var/lib/karcher-retention` — root:root `700`: `plan.json`, `action.json`,
  `last-run.json`, private `rclone.log`. Файлы — `600`. План не содержит plaintext
  компонентов/токенов, но имена/история копий всё равно не публикуются.
- Service получает write access только к двум backup roots, собственному state
  и `/root/.config/rclone` для штатного OAuth refresh. App env не читается,
  служебные порты/настройки магазина и backup cron не меняются.

После включения backup watchdog учитывает `last-run.json`: failure/повреждение
или отсутствие state, running дольше 25 минут и отсутствие успеха дольше 30 часов
дают тревогу через существующий Cronitor backup check. Третий внешний heartbeat
не нужен. Не снимать failure ради зелёного статуса без проверки причины.
Recovery inventory включает config/unit/timer/boot link, когда механизм настроен;
потеря обязательной enabled-конфигурации останавливает новый backup.

## Порядок включения

1. Запустить все Linux backup tests и unit validation. Убедиться, что config
   согласован, свежая копия проверена, pins существуют и независимый ключ сохранён.
2. Сохранить previous helpers; установить worker, watchdog/recovery updates,
   unit/timer. Под общим backup lock установить согласованный config `600`.
   До полной установки не запускать main backup с частичной enabled-конфигурацией.
3. Вызвать **plan**. Просмотреть `localDelete/cloudDelete`, точные имена и объём;
   нулевой exit сам по себе не означает применения. Если облако не читается,
   `run` не вызывать, файлы не перезаписывать без отдельного решения.
4. После разрешения на очистку выполнить service вручную, проверить число
   удалений, содержимое/целостность survivors и pins, backup/retention health.
5. Включить timer, проверить следующее расписание и отсутствие failed units.
   Создать новый полный backup с recovery-конфигурацией и проверить cloud export.
6. Убедиться, что при тестовой ошибке retention watchdog показывает failure
   (только изолированный тест, не повреждать рабочие копии).

```sh
sudo python3 -B /usr/local/lib/karcher-backup/retention.py plan
# Только с согласованным enabled=true:
sudo systemctl start karcher-backup-retention.service
sudo systemctl enable --now karcher-backup-retention.timer
```

Отключение: `systemctl disable --now karcher-backup-retention.timer`, затем
проверка, что worker уже не выполняется, и перевод config в `enabled: false`
под backup lock. Это не возвращает уже удалённые локальные файлы; облачные
наборы можно вернуть из корзины через аккаунт владельца. Не очищать всю корзину.

## История подготовки до разрешения владельца

20 октября read-only аудит: 50 полных локальных plaintext наборов (~803 MiB),
27 локальных ciphertext (~474 MiB), 27 новых облачных (~474 MiB), 23 старых
открытых облачных (~330 MiB). VPS free ~42 GiB, Disk free ~5,4 GiB. Суточный
набор `2026-10-20_00-30-01_UTC` успешно подтверждён. Первое чтение истории
облака остановилось на HTTP 500. Повтор с ограниченными ретраями подтвердил
проблему `SHA256SUMS.txt` у `2026-10-18_03-56-56_UTC`; ни один набор не удалялся.
149 Linux backup tests, Node checks и unit syntax/calendar validation прошли.
Ни config, ни worker/timer/updated watchdog на VPS не установлены и не включены.
Source/staging — `/root/karcher-retention-20261020`, попытки только read-only.
Окончательная приёмка требует успешного полного read-only плана, согласования
политики и отдельного разрешения на восстановление облачного служебного файла.

## Применение на VPS — 20 октября 2026

Владелец отдельно разрешил политику выше и восстановление только служебного
`2026-10-18_03-56-56_UTC/SHA256SUMS.txt`. До перезаписи подтверждены локальные
SHA-256, совпадение скачанных ciphertext/manifest с локальными и размер/MD5
облачного файла. Повторно загружены те же 161 байт; скачивание и все checksum
успешны, ciphertext и manifest не менялись. Остальные наборы не перезаписывались.

Полный read-only план проверил все 27 новых облачных наборов и 27 локальных пар.
Изолированный systemd smoke подтвердил download/checksum, доступ к backup roots,
`NoNewPrivileges` и нулевые effective capabilities. Затем установлены config
`enabled=true`, worker, watchdog/recovery updates и service/timer; прежние helpers
сохранены для точечного отката.

Первый worker завершился в **10:45:08 по Красноярску**: шесть избыточных облачных
наборов (108 676 450 байт, ~104 MiB) перемещены в корзину, локальных удалений — 0.
Сохранены 21 облачный набор, все три pins и все 27 локальных пар. После применения
повторно сверены listing оставшихся облачных наборов, хеши и metadata локальных
копий. Все 23 legacy cloud набора (69 файлов) и старый partial остались без изменений.
Не выполнялись удаление OS snapshots или очистка общей корзины Яндекс.Диска.

Отчёты/прежние helpers — `/root/karcher-retention-20261020`; рабочие plan/action/state —
`/var/lib/karcher-retention`. В изолированных тестах watchdog ошибки/stale дают
`RETENTION_FAILED`/`RETENTION_STALE`, не меняя реальный статус и не отправляя
тестовых внешних тревог. Новый полный backup после установки проверяется отдельно;
это не заменяет восстановление БД или clean-VPS recovery drill.

### Сбой нового облачного бэкапа и точечное восстановление

Состояние до дополнительного разрешения владельца, **10:52 по Красноярску**:

Timer активен, следующий запуск — **21 октября в 08:15 по Красноярску**.
Все 149 Linux backup-тестов повторно прошли. Новый набор
`2026-10-20_03-49-01_UTC` создан локально: checksum верны, все 1287 записей tar
извлечены в private temp и сверены с live по содержимому/metadata/ACL/xattr/links;
530 recovery config records и 797 пакетов совпали. Config, service/timer,
boot link и установленные helpers включены; временное извлечение удалено.

Upload завершился, но `MANIFEST.json` нового облачного набора стабильно отдаёт
HTTP 500: три штатные проверки и дополнительные read-only скачивания не прошли.
Metadata size/MD5 совпали с локальными 234 байтами, скачанные ciphertext и
`SHA256SUMS.txt` совпали с локальными по SHA-256. Это ещё не подтверждённый
cloud export: `.last-run` остаётся `failed/offsite_verification`, `.last-success`
сохраняет `2026-10-20_00-30-01_UTC`. Watchdog честно показывает `BACKUP_RUN_FAILED`;
следующая очистка не пройдёт fresh-checkpoint guard при таком состоянии.

Новый `MANIFEST.json` не перезаписывался: предыдущее разрешение относилось только
к старому `SHA256SUMS.txt`. Для точечного восстановления нового служебного файла
нужно отдельное согласование, после него — полная проверка чтения и новый backup.
Рабочие configs, PID/NRestarts пяти служб не менялись; site/ready/notifications
в 10:52 по Красноярску отвечают 200. Новый restore БД и clean-VPS drill не выполнялись.

После отдельного согласования владельца **в 10:56:19 по Красноярску** только
`2026-10-20_03-49-01_UTC/MANIFEST.json` повторно загружен теми же 234 байтами.
Перед записью повторно проверены локальные пары, remote size/MD5 и скачанные
ciphertext/checksum. После записи весь облачный набор заново скачан, все SHA-256
и manifest/recipient совпали с локальными; остальные два компонента и локальные
файлы не менялись. Receipt — `manifest-repair-accepted.json` в private staging.
Исторический failed stamp вручную не исправлялся: здоровый статус должен вернуть
новый штатно подтверждённый backup. Финальная приёмка фиксируется отдельно в
[README](README.md) и [аудите](../../docs/production-hardening.md).

Дополнительная сверка обнаружила зависимость текстовой таблицы `systemctl
list-unit-files` от длины transient unit: менялись только выравнивающие пробелы.
Collector/verify нормализуют пробелы и порядок строк, сохраняя сравнение имён,
состояний и presets; старые inventory с padding также совместимы. Добавлены три

данных; все **152 Linux backup-теста** успешны. Различия конфигурации/пакетов по-прежнему
запрещают подтверждение бэкапа, формат и allowlist не ослаблены.
