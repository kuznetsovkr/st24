# Шифрование и восстановление бэкапов

С 17 октября 2026 новые внешние копии шифруются [age](https://github.com/FiloSottile/age)
на публичный X25519-ключ. На VPS нет соответствующего секретного ключа.
23 старых незашифрованных оригинальных набора удалены с VPS и из облака
20 октября 2026 после отдельного разрешения и проверки зашифрованных замен.
Разовый перенос истории и приёмка описаны в [LEGACY.md](LEGACY.md); сама проверка
копии не является разрешением удалить plaintext. Современные локальные открытые
копии остаются root-only и управляются retention. Независимые алерты подключены:
[ALERTS.md](ALERTS.md), ежедневная автоочистка новых наборов — [RETENTION.md](RETENTION.md).

## Где что хранится

| Место | Содержимое |
| --- | --- |
| `/var/backups/st24/<набор>` | Локальные dump и файлы без шифрования, только root |
| `/var/backups/karcher-encrypted/<набор>` | Зашифрованный экспорт, только root |
| `yadisk:karcher-backups-encrypted/v1/<набор>` | Новые зашифрованные внешние копии |
| `yadisk:st24-backups` | Пустой прежний каталог; 23 оригинальных набора отдельно удалены 20 октября 2026 |
| `/var/backups/karcher-legacy-encrypted/<исходное-имя>` | Отдельные зашифрованные экспорты старой истории |
| `yadisk:karcher-backups-encrypted/legacy-v1/<исходное-имя>` | Архивный namespace вне ежедневной автоочистки |
| `/etc/karcher-backup/recipients.txt` | Только публичный ключ на VPS, root:root `600` |
| `$HOME/.config/karcher-backup/identity.txt` на ПК | Секретный ключ восстановления, вне проекта |
| Менеджер паролей владельца | Отдельная копия секретного ключа, сохранение подтверждено владельцем |

На Windows каталог ключа закрыт NTFS ACL: владелец, SYSTEM и Administrators.
Python 3.13 может обозначать владельца правилом `OWNER RIGHTS` (`S-1-3-4`);
это не разрешение для всех пользователей. Не показывайте ключ в чатах,
CI-логах и терминалах с записью вывода. Не копируйте его на VPS или в Git.

На текущем ПК age v1.3.2 установлен в
`$env:LOCALAPPDATA\karcher-backup-tools\age-v1.3.2\age`.
SHA-256 официального Windows zip был сверен с метаданными релиза GitHub.
На VPS установлен пакет age из подписанного репозитория Ubuntu без обновления
остальных пакетов. Для этой схемы используются обычные X25519-ключи, не PQ-ключи.

## Что делает ежедневный скрипт

Сначала проверяет публичный ключ, затем создаёт и проверяет локальные
`st24_db.dump`, `st24_files.tar.gz` и `SHA256SUMS.txt`. Эти три файла передаются
потоком в age; открытый промежуточный bundle не создаётся. Готовый экспорт
содержит только:

```text
backup.tar.age
MANIFEST.json
SHA256SUMS.txt
```

В MANIFEST находятся версия формата, время, список фиксированных компонентов
и SHA-256 публичного recipient-файла. Персональных данных и секретного ключа
в этой метаинформации нет. Перед выгрузкой экспорт публикуется локально
атомарным переименованием; `rclone copy/check` получают **только каталог
зашифрованного экспорта**, а не каталог открытых dump.

Нет режима автоматического отката на незашифрованную выгрузку. При неверном
ключе, ошибке шифрования или сохраняющейся ошибке проверки запуск завершится
ненулевым кодом. Старые копии сохранятся. В `/var/backups/st24/.last-run.json`
для нового режима есть `encryption: age-x25519-v1`.

`status: verified` подтверждает локальные проверки и совпадение скачанного
зашифрованного содержимого с экспортом. Это **не** ежедневная расшифровка:
секретного ключа на VPS нет. Периодически повторяйте восстановление на отдельном
компьютере. Контроль свежести/свободного места подключён через
[отдельный watchdog и Cronitor](ALERTS.md).

## Восстановление без исходного VPS

Для новых копий от 19 октября есть актуальная инвентаризация окружения и
[порядок восстановления на другом VPS](RECOVERY.md). Age-формат и три внешних
файла не изменились; дополнительные настройки находятся внутри `st24_files.tar.gz`.

Понадобятся собственный доступ к Яндекс.Диску, секретный ключ из менеджера
паролей, age и Python 3.11+. Проверку выполняйте на доверенном компьютере,
в закрытом каталоге вне проекта и общих облачных папок.

1. Через браузер скачайте из нужного каталога на Диске все три файла экспорта.
   Доступ к старому VPS для этого не требуется.
2. Возьмите `encrypted_backup.py` из этой версии репозитория. Секретный ключ
   сохраните в закрытом `identity.txt`, не в каталоге скачанных бэкапов.
3. На текущем Windows-ПК команда выглядит так (подставьте имя скачанного набора;
   выходной каталог должен отсутствовать или быть пустым):

   ```powershell
   $Private = Join-Path $env:USERPROFILE '.config\karcher-backup'
   $Age = Join-Path $env:LOCALAPPDATA 'karcher-backup-tools\age-v1.3.2\age\age.exe'
   python ops/backup/encrypted_backup.py open `
     --source (Join-Path $Private 'downloaded-set') `
     --output (Join-Path $Private 'restored-set') `
     --identity (Join-Path $Private 'identity.txt') --age $Age
   if ($LASTEXITCODE -ne 0) { throw 'Восстановление не прошло проверку' }
   ```

4. Продолжайте **только** после `verified: true` и нулевого кода завершения.
   В выходном каталоге будут dump, архив файлов и внутренние контрольные суммы.
   Утилита запрещает symlink, sparse-файлы, дубликаты, неожиданные имена и
   выход за каталог; владельцы и разрешения из tar не применяются.
5. Восстанавливайте PostgreSQL сначала в новую временную БД под прикладной
   ролью без superuser. До `pg_restore` проверяйте `SELECT current_database()`;
   не используйте рабочую БД или `--create` для проверки.
6. Конфигурацию nginx, сертификаты и `.env` из архива файлов переносите отдельно,
   проверяя назначения и права. Не распаковывайте весь архив вслепую поверх `/`.
   Новые копии также содержат настройки SSH/firewall и публичные разрешённые
   ключи. Перед включением SSH policy убедитесь, что ключ восстановления доступа
   уже разрешён и новое подключение работает. Не перезаписывайте SSH-конфиги
   и системные symlink вслепую: сначала подготовьте резервный доступ, установите
   nftables/loader, проверьте правила и только затем восстанавливайте автозапуск.
7. После проверки удалите только созданные временные plaintext-файлы и БД.
   Ключ и единственную пригодную копию не удаляйте.

age обеспечивает шифрование и проверку целостности ciphertext, но не подпись
отправителя; одни SHA-256 также не доказывают происхождение копии. Доверяйте
источнику архива и не запускайте его содержимое как код.

При замене ключа сохраните старый: существующие архивы останутся зашифрованы
на прежний ключ. Не заменяйте recipient-файл на VPS до сохранения нового
секретного ключа вне сервера и проверки полного восстановления.

## Проверено 17 октября 2026

Набор `2026-10-17_04-57-48_UTC` (`11:57` по Красноярску) создан новым скриптом,
выгружен, проверен скачиванием и отдельно скачан обратно из облака. На Windows
он расшифрован настоящим локальным ключом; обе внутренние SHA-256 совпали,
архив файлов читается. Dump возвращён на VPS **без ключа**, сверен с исходником
и восстановлен в уникальную тестовую БД: 26 заказов, 42 товара, 9 пользователей,
3 заявки, 1 outbox-событие и 9 проверенных внешних ключей. Тестовая БД и
временный загруженный dump удалены. Рабочая БД не изменялась, API readiness — 200.

На VPS отчёт доступен root в
`/var/backups/st24/.encrypted-restore-verified.json`. Копия ключа в менеджере
паролей подтверждена владельцем; секретный ключ на VPS не передавался.

Автоматическое удаление проверочных файлов на Windows заблокировано средой
выполнения. Под закрытым `$HOME/.config/karcher-backup` остались только
проверочные каталоги `opened-check-20261017T045748Z` (расшифрованные компоненты)
и `encrypted-check-20261017T045748Z` (скачанный ciphertext); их можно очистить
вручную после проверки. Доступ к ним подтверждён только для владельца, SYSTEM
и Administrators. **Не удаляйте `identity.txt` и сохранённую копию ключа.**

Тесты используют только отдельные синтетические ключи и данные. Проверены
реальный age roundtrip на Windows/Linux, неверный ключ, изменение ciphertext
с пересчитанными внешними SHA-256, неверный recipient, небезопасные tar-элементы
и отсутствие открытых компонентов среди файлов внешнего экспорта.

Набор `2026-10-17_14-06-57_UTC` отдельно подтвердил покрытие SSH/firewall:
скачан именно облачный экспорт, локально проверены все SHA-256 и age MAC,
11 записей внутри архива совпали с живыми настройками. Расшифровка выполнена
потоком в памяти, без записи новых открытых dump/архивов на ПК и без передачи
ключа на VPS. Сохранён только новый ciphertext в закрытом каталоге
`$HOME/.config/karcher-backup/encrypted-security-check-20261017T140657Z`.
Это проверка состава/расшифровки, не повторное восстановление БД этого набора.

## Проверено 19 октября 2026

Набор **`2026-10-19_11-17-59_UTC`** после успешного upload/downloaded-content
comparison заново скачан из Яндекс.Диска и расшифрован настоящим локальным
ключом на Windows потоком. Age authentication и все внешние/внутренние SHA-256
успешны. Проверены 526 записей нового recovery manifest и соответствие трёх
installed backup tools локальным исходникам; архив содержит 1281 запись.
На VPS отдельно проверено извлечение всех файлов с mode/owner/ACL/xattr/links.

Identity не покидал ПК; открытые компоненты на ПК не записывались. Сохранены
только ciphertext в `$HOME/.config/karcher-backup/encrypted-recovery-check-20261019T111759Z`
и безопасный `recovery-check-20261019T111759Z.json`. Новый dump не восстанавливался
в PostgreSQL; реального clean-VPS recovery drill в этом шаге не было.

## Проверено 20 октября 2026: старая история

Все **23 legacy набора** (69 исходных файлов, 345 563 784 байта) получили
зашифрованные копии с сохранением исходных имён в
`/var/backups/karcher-legacy-encrypted` и `yadisk:karcher-backups-encrypted/legacy-v1`.
Все новые exports скачаны и сверены с локальными по SHA-256. На этапе копирования
старые originals и современные наборы не менялись; отдельный export создавался,
а не подменял историю. Последующее согласованное удаление описано ниже.

В **11:32 по Красноярску** все 23 exports дополнительно проверены настоящим
локальным ключом на Windows: все 69 SHA-256 соответствуют cloud-verified receipts,
age authentication, размеры и SHA-256 всех трёх расшифрованных компонентов и
внутренние checksum совпали с исходниками. Поток полностью дочитан после tar EOF;
открытые компоненты не записывались и identity на VPS не передавался. NTFS ACL
проверены: текущий пользователь, SYSTEM и Administrators. Сохранены encrypted
exports и metadata в `$HOME/.config/karcher-backup/legacy-check-20261020`; временные
транспортные tar на VPS и ПК удалены, сам identity не тронут.

Старый `2026-10-05_03-30-01/SHA256SUMS.txt` стабильно возвращал HTTP 500. Оба
payload скачаны и совпали по SHA-256 с проверенными локальными; local checksum
совпал с cloud size/MD5. В plan записан отдельный source-read warning — это не
исправление старого cloud объекта. Ни один старый объект не перезаписывался;
условное разрешение владельца на повторную загрузку **новых** служебных файлов
в этом переносе не потребовалось. Порядок и ограничения — [LEGACY.md](LEGACY.md).

Все 175 Linux backup-тестов прошли. Это проверка сохранности/расшифровки каждого
старого набора, **не** restore 23 БД или clean-VPS drill.

После отдельного явного разрешения владельца в **11:51:17 Красноярск** завершено
удаление ровно этих 23 plaintext-наборов с VPS и Яндекс.Диска: по 69 файлов /
345 563 784 байта. Перед удалением все encrypted exports снова скачаны и сверены
по SHA-256; на ПК повторно проверены ключом без записи plaintext. Облачное удаление
безвозвратное, без очистки общей корзины. Все 23 encrypted набора в трёх местах
сохранены; остальные modern/pinned/partial копии не затронуты. Современные
локальные plaintext-копии остаются под root-only доступом и обычной retention.
Итог — `/var/lib/karcher-legacy-migration/originals-retired.json`; исторические
отчёты копирования и PC-проверки не переписываются. Подробнее — [LEGACY.md](LEGACY.md).
