# Независимые оповещения о бэкапах

`backup_health.py` читает только root-only отметки и метаданные файлов копий,
считает свободное место и отправляет два отдельных сигнала в Cronitor.
Этот внешний сервис замечает и `state=fail`, и пропажу сигналов при остановке
VPS, таймера или самого watchdog. Telegram отправляет сервис, а не магазин:
прокси приложения и его боты здесь не используются. Второй VPS не требуется.

Это не внешний HTTP-тест сайта и не замена основного `monitor/`. Watchdog
не проверяет доступность магазина для посетителей, не выполняет новое
восстановление БД и не перечитывает всё облако каждые пять минут.

## Что проверяется

- Последняя попытка не завершилась ошибкой. Обнаруженная ошибка отправляется
  в сервис в ближайший запуск watchdog, обычно в пределах пяти минут.
- После последнего `verified / complete / age-x25519-v1` прошло не более
  **26 часов**. Отсутствие очередного задания cron тоже обнаружится.
- Незавершённое задание не работает дольше **2 часов**. Пока оно идёт в пределах
  этого срока и предыдущая копия свежая, это не считается ошибкой.
- Успешный набор существует в обоих локальных хранилищах: dump, архив и суммы;
  шифрованный экспорт, манифест и суммы. Компоненты не пустые, не симлинки,
  имеют закрытые права. Наличие каталога само по себе не доказывает успех.
- На файловых системах обоих хранилищ доступно не меньше **5 ГиБ** и **15%**
  места, а также **10%** inode, если файловая система предоставляет их учёт.
  Используется `f_bavail`: резерв файловой системы для root не считается
  доступным приложению местом. Исчерпание облачной квоты будет обнаружено как
  ошибка выгрузки, но отдельного упреждающего контроля квоты здесь пока нет.

Будущие/повреждённые отметки, неизвестный формат и отсутствие обязательных
файлов считаются ошибками, а не «всё хорошо». Статус `verified` означает
подтверждённую загрузку и сверку скачанного ciphertext на момент копирования;
это не постоянное доказательство сохранности облака или восстановления БД.

## Настройка внешнего сервиса владельцем

1. Создать свой аккаунт [Cronitor](https://cronitor.io/); доступен вход через
   GitHub. Для двух проверок достаточно квоты бесплатного Hacker-плана:
   [тарифы](https://cronitor.io/pricing), [доступность Telegram](https://cronitor.io/docs/integrations).
   Платную подписку и пробный период с последующим списанием не оформлять.
2. Открыть [создание Heartbeat](https://cronitor.io/app/monitors/new/heartbeat).
   В **Name** ввести `Karcher — бэкапы`, Group и Tags оставить пустыми.
   В **Event Assertions** выбрать `heartbeat.schedule`, значение
   `every 5 minutes`. Ниже в настройках **Grace Period** указать 10 минут
   (600 секунд). Сохранить формой внизу страницы.
3. Аналогично создать `Karcher — диск`. Если есть поле Key, использовать
   `karcher-backup` и `karcher-storage`; автоматически выданные разные ключи
   тоже подходят. Это именно **Heartbeat**, не ежедневный Cron Job и не
   HTTP Check: процесс контролирует состояние каждые пять минут, а не создаёт копии.
4. Для обеих проверок не добавлять дополнительную задержку по числу ошибок:
   `failure_tolerance = 0`. Grace относится к опозданию heartbeat и не
   откладывает явный `state=fail`. См. [параметры API](https://cronitor.io/docs/monitors-api).
5. Подключить [Telegram](https://cronitor.io/docs/using-telegram-with-cronitor):
   открыть `@CronitorBot`, отправить `/start@CronitorBot`, перейти по его ссылке
   и подтвердить интеграцию. Через Settings → Alerts добавить Telegram
   в Notification List и назначить этот список **обоим** мониторам. Желательно
   оставить почту вторым каналом. Одна привязка бота ещё не назначает получателей.
6. Скопировать из каждого монитора полный базовый Telemetry URL вида
   `https://cronitor.link/p/<telemetry-key>/<monitor-key>` — без `?state=...`,
   без команды curl. Поддерживается также `https://eu.cronitor.link/p/...`.
   Нужен telemetry-only ключ для отправки событий, не management/API-admin ключ.
   Даже ограниченные URL позволяют подделывать сигналы, поэтому у нас они
   считаются закрытыми: не отправлять в чат, Git, команды или скриншоты.

При прекращении сигналов с интервалом 5 минут и grace 10 минут ожидается
тревога приблизительно через **15 минут после последнего сигнала**, если не
заданы дополнительные допуски/паузы. Это нужно подтвердить приёмочным тестом.
Явная ошибка `state=fail` срабатывает раньше; здоровый запуск передаёт `state=tick`.
См. [Heartbeat monitoring](https://cronitor.io/docs/heartbeat-monitoring)
и [Telemetry API](https://cronitor.io/docs/telemetry-api).

## Установка на VPS оператором

Не устанавливать эти файлы вместо работающего API и не запускать broad-deploy.
Сначала сохранить предыдущие root-only инструменты для отката. Установить:

```sh
install -o root -g root -m 0700 ops/backup/backup_health.py /usr/local/lib/karcher-backup/backup_health.py
install -o root -g root -m 0700 ops/backup/karcher-backup.sh /usr/local/lib/karcher-backup/karcher-backup.sh
install -o root -g root -m 0644 ops/backup/karcher-backup-health.service /etc/systemd/system/
install -o root -g root -m 0644 ops/backup/karcher-backup-health.timer /etc/systemd/system/
systemd-analyze verify /etc/systemd/system/karcher-backup-health.service /etc/systemd/system/karcher-backup-health.timer
systemctl daemon-reload
```

При обновлении более старого backup-скрипта сначала выполнить обычный успешный
бэкап: именно он создаст `.last-success.json`. Нельзя создавать эту отметку
по наличию файлов, старому restore-отчёту или одному успешному OAuth.
Проверка без сети и без изменения копий:

```sh
/usr/local/lib/karcher-backup/backup_health.py check
```

Затем владелец в **своём** терминале выполняет:

```powershell
ssh -t karcher-firstvds /usr/local/lib/karcher-backup/backup_health.py configure
```

Два URL вводятся скрыто. Проверяются HTTPS, точный разрешённый домен, формат
пути `/p/<key>/<monitor>`, отсутствие userinfo/query/fragment и различие
мониторов (даже если токены или региональные домены различаются).

В Cronitor нет используемого ранее Healthchecks `/log`. Поэтому конфигуратор
собирает **реальный текущий** отчёт и отправляет `tick` или `fail` для каждой
проверки. Возможны настоящие уведомления об ошибке или восстановлении уже
на этом шаге; конфигуратор не отправляет выдуманный «всё хорошо».
Только после двух принятых HTTP-запросов конфигурация атомарно устанавливается
в `/etc/karcher-backup/alerts.json`, root:root `600`, каталог `700`.
При отказе старый файл не заменяется. Первый сигнал мог быть принят, даже
если второй не удался: HTTP-запросы не являются общей транзакцией.

Формат конфигурации: `version: 2`, `provider: cronitor`, `checks` и `limits`.
Старая конфигурация Healthchecks версии 1 не интерпретируется как Cronitor:
требуется повторный `configure`. На текущем VPS старых URL не было установлено.

HTTP 2xx означает только **принятие запроса**, не доказательство сохранённого
события, правильного расписания или доставки уведомления. Cronitor может
автоматически создать монитор при ошибке в его ключе, поэтому до включения
таймера проверить на страницах **двух нужных** мониторов входящие события:
UTC-время, состояния и коды `BACKUP_VERIFIED` / `DISK_SPACE_OK` либо фактические
ошибки из отчёта. Не считать сам текст успешного конфигуратора приёмкой.

## Включение и приёмка

После настройки оператор выполняет:

```sh
systemctl start karcher-backup-health.service
systemctl enable --now karcher-backup-health.timer
systemctl list-timers karcher-backup-health.timer
journalctl -u karcher-backup-health.service -n 5 --no-pager
```

Подтвердить, что обе нужные проверки в сервисе здоровы, и получить настоящее тестовое
уведомление об ошибке и восстановлении. Для этого использовать отдельную
тестовую проверку или согласованный тест `state=fail` → `state=tick`; не портить
настоящие бэкапы, не подделывать success-отметки и не забивать диск. Отдельно
проверить отсутствие сигналов: для тестовой проверки дождаться Down при
пропуске интервала + Grace и затем её восстановить. Пока доставка и dead-man
не проверены, не считать оповещения полностью принятыми.

HTTP-запросы идут напрямую, без переменных HTTP(S)_PROXY, с таймаутом 10 секунд,
без перенаправлений. Временные сетевые ошибки, HTTP 429 и 5xx повторяются
один раз после паузы 1 секунда; 401/403 и остальные отказы не повторяются.
Обе проверки отправляются независимо: отказ первой не пропускает вторую.
Сервис получает только коды состояния, UTC-время и агрегаты места на диске —
без архивов, паролей, персональных данных и содержимого конфигураций.
Параметры `state`, `env=production` и безопасный JSON в `message` передаются
через query: Cronitor игнорирует POST body. Сырые HTTP-ошибки, тела ответов
и полные URL не печатаются. `delivery: accepted` в отчёте — именно HTTP-приём,
а не доказанное уведомление Telegram.

Watchdog работает от root, поскольку нельзя открывать резервные копии
пользователю приложения. В systemd используется read-only sandbox, пустой
набор capabilities, запрет повышения привилегий и доступа к home; менять
копии или конфигурацию процесс watchdog не может. Не публиковать metadata
через nginx и не выдавать внешнему мониторингу root SSH ради этой проверки.

Пороговые значения хранятся в `limits` конфигурации; менять через root-only
редактор и снова запускать `check`. URL остаются закрытыми. Архив приложения
включает `/etc/karcher-backup` (конфигурацию оповещений тоже), поэтому при
восстановлении соблюдать те же ограничения, что для `.env`. Unit-файлы
восстанавливаются из этого каталога репозитория отдельно.

## Проверки исходников

```sh
npm run test:ops
shellcheck ops/backup/karcher-backup.sh ops/backup/st24-backup.sh
python3 -m unittest discover -s ops/backup -p 'test_*.py'
systemd-analyze verify ops/backup/karcher-backup-health.service ops/backup/karcher-backup-health.timer
```

POSIX-права, Bash и root-only конфигуратор проверяются на Linux; Windows
прогоняет переносимую часть с тестовыми каталогами и замоканными HTTP-запросами.
Тесты не отправляют сообщения и не используют реальные Telemetry URL.
