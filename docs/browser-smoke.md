# Браузерные smoke-тесты витрины

Это регрессионные тесты настоящей production-mode React/Vite-сборки на
синтетическом API, **не непрерывный мониторинг production**. Сервер, реальные
боты, заявки, заказы, OTP и платежи при запуске не используются.

## Что проверяется

10 сценариев выполняются в двух профилях Chromium: desktop и мобильная
эмуляция Pixel 7. Это 20 проверок, не тестирование Safari/iOS или физического
Android-устройства.

- Главная: React отрисовал товары, заголовок и локальная таблица стилей загружены.
- Переход из меню в каталог, затем в категорию и карточку товара.
- Добавление товара в гостевую корзину, изменение количества, сумма, ограничение
  по остатку и сохранение после перезагрузки.
- Удаление последнего товара и пустая корзина после перезагрузки.
- Отсутствующий остаток: кнопку покупки нельзя нажать.
- Оформление гостем открывает авторизацию; прямой `/checkout` её не обходит.
- Ошибка API категорий не оставляет бесконечную загрузку.
- Отсутствующий товар показывает понятный экран с возвратом в каталог.
- Ошибка загрузки lazy JS chunk показывает fallback; «Обновить страницу»
  действительно восстанавливает маршрут.
- Зависший lazy chunk срабатывает по текущему 15-секундному таймауту и тоже
  восстанавливается после обновления. В тесте часы браузера ускоряются.
- Неизвестный URL показывает SPA-страницу 404.

Некоторые пункты проверяются внутри одного пользовательского сценария.
Неожиданные JavaScript `pageerror` и ошибки загрузки локальных JS/CSS проваливают
тест. Исключения для искусственно испорченного Catalog chunk заданы только в
двух соответствующих негативных сценариях и ограничены конкретными ошибками.

## Безопасность и изоляция

`tests/browser/server.mjs` проверяет TypeScript клиента, собирает отдельный
`client/dist-browser` и запускает Vite preview на **`http://127.0.0.1:4178`**.
`client/dist` и исходники приложения не перезаписываются. Если порт занят,
тест завершается ошибкой, а не подключается к неизвестному серверу.

Сборка использует фиксированный `tests/browser/settings.mjs` с публичными
синтетическими значениями и существующую allowlist/sanitizer конфигурации клиента.
Файлы `.env` отключены, унаследованные `VITE_*` заменены. API задан как
`https://api.browser.test` и целиком перехватывается браузерной fixture:

- Только GET/HEAD/OPTIONS, заранее описанные маршруты API и тестовые ответы.
- POST/PUT/PATCH/DELETE и другие методы блокируются, в том числе на mock-origin.
- Неизвестные API, внешние адреса и URL с credentials блокируются и проваливают
  тест; на настоящий сервер они не пересылаются.
- Известный Google Fonts CSS и скрипт CDEK подменены пустыми ресурсами.
  Наличие/работоспособность реальных шрифтов и виджета этим не проверяется.
- Только статические запросы к фиксированному loopback preview идут в сеть.
  Service workers выключены, WebSocket-соединения запрещены.
- У каждого теста новый изолированный browser context: корзина и cookies не
  наследуются от личного браузера или другого теста.

Четыре Node.js unit-теста отдельно проверяют эту сетевую политику. Нельзя
отключать блокировку неизвестного адреса или заменять её общим `continue()` ради
зелёного результата: новые зависимости нужно явно моделировать. Не добавлять
сюда production URL, реальные credentials или токены.

## Локальный запуск

Нужна поддерживаемая проектом Node.js. После установки зависимостей один раз
скачать Chromium; эта установка обращается к серверам Playwright, сами тесты — нет.

```sh
npm ci
npx playwright install chromium
npm run lint:browser
npm run test:browser:types
npm run test:browser:policy
npm run test:browser
```

В Linux для системных библиотек браузера при необходимости:
`npx playwright install --with-deps chromium`.

`npm run test:browser -- --project=chromium-mobile` запускает только мобильный
профиль. Для поиска нестабильности: `npm run test:browser -- --repeat-each=2`.
Не запускать два browser-runner одновременно: они используют один локальный порт
и выходной каталог. Главные unit-тесты `npm test` включают только лёгкие проверки
сетевой политики, но не устанавливают и не запускают браузер.

После запуска HTML-отчёт находится в `playwright-report/index.html`. При падении
в `test-results/` сохраняются screenshot и trace; `npx playwright show-report`
открывает локальный просмотр. Эти каталоги и отдельная сборка исключены из Git.
Содержимое отчётов синтетическое, но при изменении fixtures всё равно не допускайте
попадания реальных данных в диагностические артефакты.

## CI и границы приёмки

В `.github/workflows/ci.yml` добавлен отдельный job `browser-smoke`:
`npm ci` → установка Chromium → lint/typecheck/network-policy → browser tests.
Отчёт и диагностика сохраняются как artifact на 7 дней. Используются существующие
события workflow: push в master, pull request, ручной запуск и недельное расписание.
Секреты репозитория и production API для job не нужны.

Добавление YAML локально **не означает удалённый запуск CI**. Для этого нужны
коммит/публикация в репозиторий и успешный запуск в GitHub Actions. Проверяйте
результат именно опубликованного commit SHA; отдельный VPS не требуется.
Публикация тестов в GitHub сама по себе не является деплоем магазина на сервер.

Тесты доказывают работу клиентской сборки на известных ответах API. Они не
доказывают доступность живого каталога/фотографий, корректность backend API,
авторизацию по OTP, расчёт доставки, оформление авторизованным пользователем,
платёж, Telegram-уведомление или реальный CORS сервера. Эти интеграции проверяются
отдельно. Регулярные проверки production через Cronitor и их приёмку нужно
сохранять: [HTTP checks](../ops/monitoring/README.md),
[Telegram](../ops/monitoring/TELEGRAM.md).

Использованные механизмы Playwright: [local webServer](https://playwright.dev/docs/test-webserver),
[API mocking](https://playwright.dev/docs/mock), [CI](https://playwright.dev/docs/ci-intro).
