# Единые технические имена

Канонический префикс — `karcher`, читаемое название — `Karcher`.

| Объект | Имя |
| --- | --- |
| Корневой npm-пакет / пакет монитора | `karcher` / `karcher-external-monitor` |
| API unit, системный пользователь и группа | `karcher-api` |
| Настройки API и публичной сборки | `/etc/karcher/api.env`, `/etc/karcher/client.env` |
| Логи API | `/var/log/karcher-api/api.log` |
| Отдельный монитор | `karcher-monitor-*`, `/etc/karcher-monitor`, `/var/lib/karcher-monitor` |
| Локальная папка проекта | `C:\development\karcher` |

Домен магазина, GitHub-репозиторий `st24`, PostgreSQL и `/var/www/st24` не меняют
имена: это самостоятельная идентичность магазина, не сокращение проекта.
История бэкапов, имена уже созданных наборов и форматы шифрования сохраняются.

## Совместимость браузера

Новые сессии получают `karcher_auth_token` и `karcher_csrf_token`. Уже выданные
`her_auth_token` / `her_csrf_token` читаются с прежним JWT secret до обычного
истечения сессии; новые cookie имеют приоритет. CSRF по-прежнему требует
совпадения заголовка, cookie и значения в подписанном JWT. Выход очищает оба
поколения cookie, поэтому старая сессия не может «воскреснуть» после выхода.

Гостевая корзина читается из `karcher_cart_v1`, а при отсутствии этого ключа —
из старого `her_cart_v1`. При первом сохранении появляется новый ключ, старая
копия не удаляется. Пустая новая корзина не заменяется старой. Серверные корзины,
заказы и пользователи в БД не переименовываются и не пересоздаются.

## Переход действующего сервера

Это миграция службы, а не массовая замена строк в `/etc`. Перед ней нужны свежий
проверенный offsite backup, снимок unit/config/ACL и независимый таймер отката.
Релиз предварительно собирается и проверяется; dump восстанавливается только
в отдельную временную БД. Во время переключения API кратковременно останавливается.

Системные пользователь и группа переименовываются **с сохранением UID/GID**:
это сохраняет числовое владение и ACL существующих uploads/tmp/logs. Каталог
настроек `/etc/her` переносится в `/etc/karcher`, логов `/var/log/her-api` —
в `/var/log/karcher-api`. Значения секретов не меняются. Меняются unit,
tmpfiles/logrotate, boot-ссылка и checkout `.env`-ссылки; старая служба не должна
запускаться одновременно с новой на одном порту или читать Telegram updates.

Обновлённый backup-скрипт устанавливается после удаления старых активных ops-файлов
и проверяет новый полный набор. Обнаружив старый или смешанный layout, он явно
отказывает, а не подтверждает копию из устаревшего `.env`. После приёмки проверяются
новый backup, права nginx, состояние ботов, boot startup и отсутствие старой службы.
Только затем отключается автооткат. Откат миграции не восстанавливает рабочую БД.

Старые имена намеренно остаются в исторических отчётах, архивных копиях и коде
совместимости. Архивы прежнего layout восстанавливают сначала по соответствующей
версии инструкции; нельзя вслепую накладывать их systemd/config поверх нового.
