Текущие технические имена после унификации: `karcher-api.service` и
`/etc/karcher/api.env`. Ниже сохранены фактические имена и команды прошлых этапов;
для актуального перехода см. [правила именования](../../docs/project-naming.md).

## Проверено 17 октября 2026

Новый `TELEGRAM_OUTBOUND_PROXY_URL` был сохранён в production `.env`, но работающий
с 10 октября API продолжал использовать старое значение. Сопоставление файла и
окружения процесса показало единственное различие — proxy URL. Токены трёх ботов,
режимы и остальные параметры совпали; значения секретов не печатались.

Отдельный read-only процесс с установленными Node.js/undici и proxy dispatcher
production-приложения выполнил `getMe` и `getWebhookInfo` через новый прокси для
`main`, `orders`, `b2b`: все шесть ответов HTTP 200/`ok: true`, ожидаемые webhook
URL совпали, `pending_update_count: 0`, ошибок webhook нет. Это проверяет соединение
и конфигурацию, **не доказывает реальный sendMessage** или входящий end-to-end сценарий.

До перезапуска создан зашифрованный offsite backup `2026-10-17_15-57-28_UTC`,
выгрузка и скачанное содержимое проверены штатным backup-скриптом. Затем выполнен
только `systemctl restart her-api.service`, без деплоя/сборки/миграции на новую версию.
Существующие правки `deploy.sh`/`package-lock.json` на VPS не трогались.

Новый API PID — `327914`; окружение процесса содержит актуальный proxy URL.
Локальная readiness восстановилась примерно за 1,6 с после команды restart;
публичные сайт и readiness — HTTP 200, PostgreSQL/uploads `ok`. Это не замер полной
длительности недоступности при остановке. Все три bot status стали `ok`, worker
работает, outbox pending/retry/dead — 0, число рабочих получателей осталось 3/4/3.
Nginx, firewall и настройки webhook не менялись.

Это был первый успешный замер, а не окончательная приёмка. При повторном наблюдении
Telegram сообщил `Connection timed out` при доставке входящих webhook на правильный
IP магазина. У main/orders накопилось по пять updates; у B2B некоторые реальные
webhook получили HTTP 200, но также зарегистрированы таймауты. Отдельные свежие
запросы `getMe`/`getWebhookInfo` через новый proxy продолжали успешно отвечать.
В integration events supervision зафиксирован `webhook_delivery_error`, а не
ошибка исходящего proxy. Поэтому текущую доставку Telegram нельзя считать
полностью восстановленной по первому успешному `getMe`.

Отрицательные внешние POST `{}` без секретного webhook header отклонены всеми
тремя маршрутами с HTTP 403. Firewall/Fail2ban не отключались; IPset старой панели
пуст, явных deny-правил панели нет. Причина входящих сетевых таймаутов до конца не
локализована; исправный сайт с рабочей станции не доказывает доступность с узлов
Telegram. В 35-секундном двунаправленном наблюдении на ens3 зарегистрированы 5 SYN
от официальных Telegram-подсетей и 13 исходящих SYN-ACK, но нет завершающего ACK.
В этих попытках соединение не дошло до TLS/HTTP. Это указывает на TCP-доступность
между сторонами, но не доказывает конкретного виновника на сетевом пути.

`drop_pending_updates: false`, затем установлен новый env и запущен тот же API.

Отдельный ручной `getUpdates` не выполнялся: единственный consumer — API.

Итоговый API PID `328757`. После первого long-poll и повторных supervision
циклов все три бота в режиме `polling`/`ok`, worker здоров, получатели остались
3/4/3, outbox pending/retry/dead — 0. Окружение процесса совпало с файлом; других
env-изменений нет. Публичные сайт/readiness — 200; на этом этапе старый failed lead был

Сохранён новый зашифрованный offsite набор `2026-10-17_16-17-34_UTC`: штатные


нужен точечный разбор вместо полного старого файла. Новый прокси при этом сохраняется:
snapshot сделан уже после его применения.

### Почему после перехода notification health был 503

Оставалась одна старая `need_part_catalog` заявка со статусом `failed`, созданная
10 августа 2026 в 14:59:44 UTC (21:59:44 по Красноярску). У неё нет outbox-события:
обычный `outbox:redrive` неприменим. Владелец ранее считал содержимое похожим на тест.
Содержимое и контакты повторно в журнал/чат не выгружались.

После принятого перехода на polling worker и все боты были здоровы; единственный
ненулевой бизнес-invariant — `failedLeadNotifications: 1`. До отдельного согласования
историю заявки не изменяли, повторную доставку, удаление или фиктивное `sent`
не выполняли. Последующий согласованный разбор описан ниже.

### Тестовая заявка заархивирована и удалена с разрешения владельца

Владелец явно подтвердил, что заявку можно считать тестовой, сохранить её
защищённую копию и удалить из рабочей БД. Около 23:36 по Красноярску 17 октября
2026 удалена **только** запись `a9ff3a95-b820-4aad-b30d-a4bd058f6507`.
Другие две заявки не изменились: до/после совпали их число и SHA-256 содержимого.
Повторная read-only проверка: осталось 2 заявки, failed — 0, заказов — 26,
outbox-событий — 1. Статус `sent` не устанавливался, сообщения не отправлялись.

Перед удалением:

- Проверены UUID, вид, исходный статус, даты и отсутствие outbox-события,
  ссылающихся внешних ключей, пользовательских триггеров и правил таблицы.
- Все 11 полей сохранены в JSON-архиве, включая исходный `row_to_json` текст
  и точные PostgreSQL timestamps; полный backup до изменения —
  `2026-10-17_16-17-34_UTC`.
- Архив зашифрован age на существующий публичный recipient. Открытые данные
  обрабатывались в памяти и не записывались на диск/в логи.
- Зашифрованный экспорт загружен на Яндекс.Диск, проверен `rclone check --download`,
  отдельно скачан обратно из облака и перенесён на доверенный ПК.
- На ПК настоящим локальным ключом проверены age MAC, SHA-256 ciphertext/plaintext,
  все поля, UUID, статус, даты и совпадение JSON с исходной строкой. Ключ на VPS
  не передавался. Это проверка чтения/содержимого архива, **не тестовый INSERT
  или восстановление БД**.

Удаление выполнено одной транзакцией с короткой блокировкой таблицы и таймаутами.
Непосредственно перед DELETE повторно проверены связи и SHA-256 исходной строки;
изменившаяся строка не была бы удалена. DELETE обязан затронуть ровно одну запись;
остальные заявки проверены до COMMIT. При неопределённом результате COMMIT
не повторять операцию вслепую, сначала проверить БД и receipt.

Защищённые артефакты:

- VPS: `/root/karcher-telegram-recovery-20261017T155800Z/test-lead-archive/`
  (`0700`, файлы `0600`), зашифрованный экспорт в `export/`, подтверждения
  `offsite-verified.json`, `downloaded-archive-verified.json`,
  `removal-intent.json`, `removal-receipt.json`.
- Облако: `yadisk:karcher-backups-encrypted/operator-archives/2026-10-17-test-lead-a9ff3a95`,
  только `lead-request.json.age`, `MANIFEST.json`, `SHA256SUMS.txt`.
- ПК: `$HOME/.config/karcher-backup/test-lead-check-20261017T163340Z`,
  только ciphertext, manifest, суммы и безопасное подтверждение проверки;
  NTFS ACL — владелец, SYSTEM, Administrators.

Это отдельный формат `karcher-test-lead-archive-v1`, не ежедневный `backup.tar.age`;
команда `encrypted_backup.py open` к нему не применяется. Для восстановления
расшифровать age на доверенном ПК, проверить manifest/суммы и взять объект `row`
из JSON, а не весь wrapper. Сначала проверить импорт всех полей в отдельную
тестовую БД; не перезаписывать существующий UUID и не импортировать в production
без отдельного решения. Обычные полные бэкапы до удаления также сохранены.

После изменения с рабочего ПК проверены публичные readiness и notifications:
HTTP 200, root `status: ok`, JSON/no-store headers. Worker и все три polling-бота
здоровы, outbox pending/retry/dead — 0, все бизнес-инварианты — 0. API не
перезапускался, ограничения health не менялись. Эта приёмка не заменяет запуск
нового внешнего монитора в аккаунте Cronitor.

## Независимый наблюдатель без дополнительного сервера

По выбору владельца новый VPS пока не арендуется. Минимальное расширение:
добавить в существующий Cronitor HTTP-monitor
`https://xn---24-3edf.xn--p1ai/api/health/notifications`.

Backend регулярно выполняет фактические запросы к Telegram через рабочий прокси;
этот health учитывает состояния всех трёх ботов, freshness supervision, worker,
outbox и бизнес-инварианты. При отказе прокси/токена/webhook возвращается ошибка;
Cronitor проверяет endpoint снаружи и отправляет собственную тревогу через уже
подключённый `@CronitorBot`. Его доставка не использует прокси магазина. При
пропаже самого VPS внешний HTTP-запрос также не пройдёт.

Это **не развёртывание полного `monitor/` runner**: независимый сервис читает
диагностику приложения, а не самостоятельно ходит через production proxy. Нет
запланированных реальных send-canary или ежедневной полной сводки, browser smoke
и входящего Telegram user/MTProto E2E. Эти слои остаются отдельными задачами.

[Hacker](https://cronitor.io/pricing) допускает 5 monitors и минимум 5 минут;
здесь уже настроены два heartbeat и два HTTP checks. При отсутствии других
мониторов дополнительная проверка будет пятой. Документация
[интеграций](https://cronitor.io/docs/integrations) относит Telegram к бесплатным.
Перед сохранением всё равно сверить действующий тариф, число monitors и
Notification List в аккаунте; платный план/шестую проверку не подключать автоматически.

### Шаблон и приёмка

[cronitor-telegram-monitor.json](cronitor-telegram-monitor.json) — отдельный шаблон
добавления одной проверки, не замена уже настроенных четырёх и не команда к API.
Формат совместим с используемым Monitor API `2020-10-01`, настройки в аккаунте
нужно применять и проверять отдельно. Как и у двух существующих HTTP checks:
GET, every 5 minutes, timeout 10 seconds, SSL verification включена, redirects
выключены, получатели `default` с Telegram. Токены ботов, proxy и Telemetry URL
передавать в эту проверку не нужно.

Основные условия — HTTP 200, JSON root `status = ok`, `worker.status = ok`,
`outbox.dead = 0`, `invariants.failedLeadNotifications = 0`, корректные JSON/no-store
response headers. Не требовать `pending = 0` при каждом запросе: кратковременная
очередь нормальна, возраст/SLA уже учитываются самим health.

До согласованного разбора старой заявки шаблон **обязан был давать тревогу**.
Теперь заявка заархивирована и удалена с разрешения владельца, публичный health
здоров. Не менять ожидаемый status на `error` ради завершения настройки:
новые реальные нарушения должны давать тревогу. Владелец затем сообщил, что
создал monitor по инструкции и его внешняя проверка зелёная. Конфигурацию
аккаунта автоматически не читали; приёмка Telegram failure/recovery для этого
монитора пока не выполнена. Успешный HTTP-check не доказывает доставку тревоги.

Владелец решил провести этот тест позже и продолжить другие работы. Приёмка
его уведомлений остаётся открытой; неверное тестовое значение нельзя оставлять
в рабочем условии. Самостоятельно состояние формы/условий в аккаунте не проверялось.

Следующий шаг: проверить Telegram failure/recovery безопасным временным неверным
условием, не останавливая магазин/прокси. Во включённом новом мониторе изменить
только ожидаемый root JSON `status`: `ok` → `acceptance-test-not-real-outage`.
Поставить таймер на 10 минут. После тревоги именно «Karcher — Telegram и доставка»
сразу вернуть `ok`, сохранить и дождаться зелёного результата и уведомления
о восстановлении. Если за 10 минут тревога не пришла, всё равно вернуть `ok`
и отдельно разбирать доставку. Остальные мониторы, endpoint и настройки VPS
не менять. Факты доставки зафиксировать после подтверждения владельца, не
заранее. Общая процедура —
[README.md](README.md#приёмка-без-остановки-магазина).

Проверки шаблонов офлайн:

```sh
python3 -m unittest discover -s ops/monitoring -p 'test_*.py'
```

Они не обращаются к аккаунту Cronitor, не доказывают совместимость его UI и
не отправляют сообщения. Шаг включён в CI, публикация/удалённый CI отдельно.

## Отдельный тестовый чат

Владелец выбрал создание закрытой группы «Karcher — мониторинг». Добавить:

- `@st24_unavailability_bot`;
- `@st24_orders_bot`;
- `@st24_legal_entities_bot`.

Ботам достаточно права отправлять сообщения, admin-права не требуются.
Группу **не добавлять** в `TELEGRAM_*_ALLOWED_CHAT_IDS`/рабочие подписки: иначе
она начнёт получать настоящие заявки и заказы. Для явно разрешённого canary
используется отдельный chat ID; проверить тип/идентичность группы и доступ всех
трёх ботов перед отправкой. Не заменять им чаты реальных получателей.

Когда группа создана, владелец сообщает её chat ID. Если он неизвестен, можно
сначала посмотреть адрес открытой группы в Telegram Web, не отправляя session
данные/токены, и сверить ID через read-only Bot API. Не вызывать отдельный
`getUpdates` параллельно работающему API ради получения ID: consumer должен быть один.
При webhook-режиме тем более нельзя отключать регистрацию только ради ID.

После подтверждения группы — ровно по одному явно помеченному тихому тестовому
сообщению каждым ботом, затем проверить Bot API receipt и подтверждение владельца.
Тестовые сообщения и старые заявки в рабочие чаты заказчика без отдельного
разрешения не отправляются.

### Разовая проверка доставки — 17 октября 2026

Владелец сообщил chat ID; через `getMe`, `getChat` и `getChatMember` подтверждены
ожидаемые боты, закрытая supergroup «Karcher — мониторинг» без тем и право каждого
бота отправлять сообщения. Admin-права не выдавались: main/orders — обычные
участники, b2b — участник с ограничениями, разрешающими текстовые сообщения.

До и после отправки `.env` совпал SHA-256, группа отсутствовала во всех трёх

сначала проверить сообщения в группе и запись receipt.

## Следующая замена прокси

Изменение `.env` не обновляет окружение уже работающего Node.js. Сначала отдельно
проверить новый маршрут через `getMe`/`getWebhookInfo` без отправки сообщений,
сверить изменения остальных env-параметров, сделать backup. Затем короткий restart
текущего API (не запуск старого deploy.sh), проверить публичный readiness и дождаться
успешных supervision всех трёх ботов. Токены/URL не помещать в командную строку,
репозиторий, shell history или журналы; не выводить сырые сетевые исключения.

Bot API: [getMe](https://core.telegram.org/bots/api#getme),
[getWebhookInfo](https://core.telegram.org/bots/api#getwebhookinfo),
[sendMessage](https://core.telegram.org/bots/api#sendmessage).
