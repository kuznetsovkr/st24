# Резервное копирование Karcher

Текущий режим: новые внешние копии шифруются. Схема ключей, формат и проверенное
восстановление описаны в [ENCRYPTION.md](ENCRYPTION.md). Ниже также сохранены
результаты первоначальной проверки старой незашифрованной истории.

Контроль давности копий, ошибок и места на диске с независимой доставкой
описан в [ALERTS.md](ALERTS.md). Подготовленный watchdog без настроенных
Telemetry URL Cronitor, активного таймера и проверенных уведомлений ещё не является
работающим оповещением.

Скрипт работает от root и сохраняет совместимость с существующим cron:
`/usr/local/bin/st24-backup.sh` вызывает
`/usr/local/lib/karcher-backup/karcher-backup.sh`.

В `/usr/local/lib/karcher-backup` устанавливаются:

- `karcher-backup.sh` из этого каталога;
- `read-database-url.mjs` из этого каталога;
- `authorize-yandex.py` из этого каталога (ручное восстановление доступа);
- `encrypted_backup.py` из этого каталога (age, Python 3.11+);
- `backup_health.py` из этого каталога (проверка и независимые сигналы);
- `postgres-command.mjs` из `scripts/`.

Файл `st24-backup.sh` из этого каталога устанавливается как
`/usr/local/bin/st24-backup.sh`. Существующая запись cron сохраняется.

На текущем VPS расписание root-cron: `30 3 * * * /usr/local/bin/st24-backup.sh >>
/var/log/st24-backup.log 2>&1` (одна строка, ежедневно в 03:30 по часовому поясу
сервера Europe/Moscow, то есть в 07:30 по Красноярску). При переносе восстановить
эту запись отдельно.

Каталог инструментов имеет права `700`, исполняемые скрипты — `700`, модули — `600`.
Рабочие пути приложения и локальных открытых копий пока сохраняют `st24`:
`/var/www/st24`, `/var/backups/st24`. История `yadisk:st24-backups` не удалена.
Новые зашифрованные экспорты находятся в `/var/backups/karcher-encrypted` и
`yadisk:karcher-backups-encrypted/v1`. Эти пути нельзя переименовывать отдельно
от настройки скрипта и восстановления ранее сделанных копий.

## Защита и проверка

Каталоги копий доступны только root (`700`), файлы — `600`. Скрипт использует
`umask 077`, общий `flock`, таймауты команд и читает DATABASE_URL без выполнения
`.env` как shell-кода. Пароль БД не попадает в аргументы PostgreSQL-команд.

Копия содержит custom-format dump PostgreSQL и архив приложения с uploads,
исходниками, конфигурацией nginx, сертификатами и API unit. После перехода на
управляемый сервис также обязательны `/etc/her/api.env`, `/etc/her/client.env`,
tmpfiles/logrotate и существующая ссылка автозапуска API. Для дампа используется
именно `/etc/her/api.env`; неполный набор не подменяется старым `server/.env`.
Архив сохраняет ACL/xattr загрузок: при восстановлении нужны `tar --acls --xattrs`
и предварительно созданный сервисный пользователь (см. [ops](../README.md)). node_modules,
Git internals и временные каталоги исключены. Ошибки tar не игнорируются.
Набор становится завершённым только после чтения архива и проверки SHA-256.

### Настройки SSH и firewall

На VPS с установленной [защитой доступа](../security/README.md) архив также
содержит `/etc/ssh/sshd_config`, действующие `sshd_config.d/*.conf`, публичный
`/root/.ssh/authorized_keys`, конфиг и loader firewall, его systemd unit,
опциональные `karcher-firewall.service.d/*.conf`, ссылку автозапуска и маску
стандартного `nftables.service`. Приватные SSH host/user keys и ключ age
не добавляются: целиком `/etc/ssh`, `/root/.ssh` и `/root/.config` не копируются.

Файл `/etc/karcher-backup/security-required` — root:root `600`, пустой маркер
обязательного покрытия. На текущем VPS он установлен. Если marker есть или
обнаружена хотя бы часть конфигурации Karcher security, скрипт требует полный
набор, обычные файлы без symlink и точные системные ссылки автозапуска/маски.
При несоответствии запуск завершается с ошибкой `security_configuration` до
создания dump; последняя подтверждённая копия сохраняется.
На хосте, где security никогда не устанавливался и marker отсутствует,
дополнительный набор остаётся опциональным. При первом подключении включать
marker только после завершения установки и проверки доступа, не во время
частично выполненного bootstrap.

**Проверено 17 октября 2026:** набор `2026-10-17_14-06-57_UTC` создан новым
скриптом, выгружен в облако и проверен полным скачиванием. Затем экспорт
отдельно скачан из Яндекс.Диска и расшифрован локальным ключом потоком:
11 записей (настройки security, marker и обновлённый backup-скрипт) совпали
с VPS по содержимому/владельцам/правам файлов и целям/владельцам ссылок.
Проверены age authentication и внутренние/внешние SHA-256. Открытые компоненты
на ПК не записывались; новый dump в PostgreSQL в этом тесте не разворачивался.
Отчёт root-only: `/var/backups/st24/.security-export-verified.json`.
Linux-прогон backup tools: 92 теста, включая 10 новых проверок покрытия security.

После выгрузки выполняется `rclone check --download --one-way`: удалённое
содержимое скачивается для сравнения с локальным. Проверка повторяется до трёх
раз с паузой 5 секунд, если чтение не удалось; для успеха требуется полностью
успешное сравнение. При сохраняющейся ошибке облака процесс
возвращает ненулевой код; локальные копии остаются на месте. Состояние последнего
запуска записывается в `/var/backups/st24/.last-run.json`, подробные журналы —
в root-only `/var/log/karcher-backup`. Старый cron-log также должен иметь `600`.
`.last-success.json` обновляется отдельно и только после проверки скачанного
зашифрованного экспорта; ошибка следующего запуска эту отметку не затирает.
В `.last-run.json` также записываются начало задания (`running`, `startedAt`)
и промежуточное состояние `local_verified`.

Автоматическое удаление старых копий пока отключено. После проверки облака
политику хранения и очистку нужно настроить отдельно; успешная авторизация
сама их не включает. Контролируйте свободное место, не запускайте
`rclone sync/delete/cleanup` для исправления ошибки доступа.

Архивы содержат персональные данные, `.env` и закрытые ключи сертификатов.
На VPS они root-only, облачная папка не должна иметь публичных ссылок.
Новые внешние архивы дополнительно зашифрованы; соответствующий секретный ключ
хранится вне VPS. Старые внешние копии пока остаются без шифрования — их
миграцию и удаление нужно согласовать отдельно, после проверки новой схемы.

Восстановление проверяется в отдельно созданной БД с уникальным именем, под
прикладной ролью без superuser. Перед pg_restore обязательно проверить
`SELECT current_database()`; не использовать `--create` и рабочее имя базы.
После проверки удаляется только созданная временная БД.

## Восстановление доступа к Яндекс.Диску

При ответе `410 Gone` нельзя считать копии на VPS внешним бэкапом. Для общего
OAuth-приложения rclone зарегистрирована [аналогичная проблема](https://github.com/rclone/rclone/issues/10067).
Собственное OAuth-приложение — проверяемый обходной вариант, не гарантия
работоспособности API.

1. Владелец Диска создаёт [приложение для доступа к API](https://yandex.ru/dev/id/doc/ru/register-api)
   с правами `cloud_api:disk.read`, `cloud_api:disk.write`, `cloud_api:disk.info`.
   Эти права дают доступ ко всему Диску; по возможности используйте отдельный
   аккаунт для резервных копий. ClientID публичный, Client secret и токен — секреты.
2. В своём терминале владелец выполняет:

   ```powershell
   ssh -t karcher-firstvds /usr/local/lib/karcher-backup/authorize-yandex.py
   ```

3. Вводит ClientID, затем в **скрытом запросе терминала** — Client secret из
   настроек этого приложения. Скрипт печатает ссылку `response_type=code`;
   владелец открывает её, разрешает доступ и вводит **полный код подтверждения со страницы**
   в следующий скрытый запрос. Секрет и код не нужно отправлять в чат или
   помещать в командную строку. Используется [официальный поток с кодом подтверждения](https://yandex.ru/dev/id/doc/ru/codes/screen-code).
   Код рассматривается как непрозрачная строка: допустимы буквы и цифры,
   фиксированной длины и требования «7 цифр» нет. Код передаётся без преобразований.
4. Скрипт сам обменивает код на access/refresh token и настоящий срок действия,
   выполняет пробное продление, проверяет доступ через установленный rclone с
   временной конфигурацией. Только при успехе заменяет секцию `yadisk`, сохранив
   root-only rollback-файл старого конфига. В конфиге `600` сохраняются Client
   secret и обновлённая пара токенов. Секреты передаются Яндексу только в теле
   HTTPS POST, перенаправления запрещены; они не печатаются. При отказе рабочий
   конфиг не заменяется, временная конфигурация удаляется.
5. Оператор запускает `/usr/local/bin/st24-backup.sh` и проверяет, что
   `.last-run.json` имеет `status: verified`, `stage: complete`. Нужна именно
   успешная загрузка **и** проверка скачанного содержимого, не только список файлов.

Не используйте прежний поток `response_type=token`: установленный rclone 1.73.4
[требует непустой refresh_token ещё до первого запроса к Диску](https://github.com/rclone/rclone/blob/v1.73.4/backend/yandex/yandex.go#L255).
Отладочный токен без refresh_token для этого backend не подходит. Заглушки,
чужой refresh token и выдуманный срок действия не используются.

Продление использует настоящий refresh token и Client secret того же приложения.
В случае отзыва/истечения разрешения может потребоваться повторная авторизация;
работоспособность продления не отменяет независимый контроль свежести бэкапов.

Ошибки имеют безопасные коды (`REFRESH_MISSING`, `TOKEN_CLIENT_REJECTED`,
`TOKEN_CODE_REJECTED`, `REMOTE_401`, `REMOTE_403`, `REMOTE_410` и другие).
Можно сообщить код оператору, но не секреты.
Неверный формат ввода разрешается исправить в том же сеансе, до трёх попыток.

Проверки исходников:

```sh
npm run test:backup-config
shellcheck ops/backup/karcher-backup.sh ops/backup/st24-backup.sh
# Linux: используется системный модуль fcntl, как и на VPS.
python3 -m unittest discover -s ops/backup -p 'test_*.py'
```
